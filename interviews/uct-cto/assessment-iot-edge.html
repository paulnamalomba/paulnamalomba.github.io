🔌 Hardware: MCU Boards & Microcontrollers

Focus on the two primary platforms you’ll encounter in smart-mobility and infrastructure-monitoring contexts.

ESP32 — Low-Cost Wi-Fi/Bluetooth Edge Node
  • Study ESP32 architecture & capabilities
    Dual-core Xtensa LX6, 240 MHz, 520 KB SRAM, built-in Wi-Fi (802.11 b/g/n) and Bluetooth (Classic + BLE). Supports deep-sleep modes (as low as 10 µA) for battery-powered field deployments. Review the datasheet from Espressif.
  • Wokwi: Complete the ESP32 “Blink + Serial” starter
    Go to wokwi.com, select ESP32, and write a sketch that blinks an LED and prints “Hello from edge node” to Serial Monitor. Time yourself — aim for under 5 minutes. This verifies you can navigate the tool fluently.
  • Wokwi: Read a DHT22 temperature/humidity sensor
    Wire a virtual DHT22 to the ESP32 in Wokwi. Write C++ firmware using the DHT library to read temperature and humidity every 2 seconds and output via Serial. Understand the difference between analogue (ADC) and digital sensor interfaces.
  • Wokwi: Push sensor data via MQTT (PubSubClient)
    Extend the DHT22 project to publish JSON payloads ({"temp": 23.4, "humidity": 61.2, "ts": 1710000000}) to a public MQTT broker (broker.hivemq.com) using the PubSubClient library. Use topic uct/sensors/env/01. Verify receipt with MQTT Explorer or HiveMQ WebSocket client.
  • Practice ESP32 deep-sleep & wake-on-timer
    Write firmware that reads sensor data, publishes via MQTT, then enters deep sleep for 60 seconds. This is the standard pattern for battery-powered field sensors. Calculate power budget: 150 mA active × 5s + 10 µA × 55s — estimate battery life on a 2000 mAh LiPo.
Raspberry Pi — Heavier Edge Compute
  • Compare RPi vs ESP32: know when to use which
    RPi runs full Linux (Debian/Raspbian), has 1–8 GB RAM, USB/Ethernet/HDMI. Use RPi as an edge gateway that aggregates data from multiple ESP32 nodes, runs local ML inference, and forwards to the cloud. Use ESP32 as the leaf sensor node. Be able to articulate this split in the interview.
  • Study: RPi as a local Mosquitto MQTT broker
    Review how to install mosquitto on a Raspberry Pi so it acts as a local MQTT broker for a cluster of ESP32 sensor nodes. Understand the benefit: if the upstream internet link drops, the RPi buffers all sensor data locally (store-and-forward). This is critical for African deployment contexts with unreliable connectivity.
  • Study: Edge ML inference with TensorFlow Lite on RPi
    Review how a Raspberry Pi can run TFLite models to classify anomalies (e.g., pothole detection from accelerometer data or unusual vibration patterns) before sending data to the cloud. This reduces bandwidth by 90%+ and is a CTO-level optimization that will impress.

📡 Sensors for Transport & Infrastructure

GPS & Location
  • Study: NEO-6M GPS module with ESP32
    Review NMEA sentence parsing ($GPGGA, $GPRMC). The NEO-6M outputs lat/lon/alt/speed at 1 Hz via UART. Understand how to parse with the TinyGPS++ library. Relate this directly to the Ecoride GPS tracking you built — same data, different source.
  • Know RTK GPS vs standard GPS accuracy
    Standard GPS: ±2–5 m. RTK-corrected GPS: ±2 cm. In transport planning (e.g., lane-level vehicle tracking for MyCiTi BRT), RTK matters. Be ready to discuss when the cost is justified vs. when standard GPS suffices.
IMU — Accelerometers & Gyroscopes
  • Study: MPU-6050 6-axis IMU (I2C)
    3-axis accelerometer + 3-axis gyroscope. Applications: vehicle telemetry (harsh braking, cornering G-forces), structural health monitoring (bridge vibrations). Review I2C communication protocol and how to read raw registers using Wire.h on ESP32.
  • Wokwi: Simulate vibration data & compute RMS
    In Wokwi, use simulated accelerometer values. Write firmware that computes the RMS (root-mean-square) of acceleration over a 1-second window. If RMS exceeds a threshold, publish an alert via MQTT. This simulates a rudimentary structural health alarm.
  • Know sensor fusion basics (complementary filter)
    Accelerometers give noisy but absolute orientation; gyroscopes give smooth but drifting orientation. A complementary filter combines both: angle = 0.98 * (angle + gyro_rate * dt) + 0.02 * accel_angle. Know this intuitively — you may need to explain it.
Environmental Sensors
  • Study: Air quality sensors (PMS5003, MQ-135)
    Particulate matter (PM2.5/PM10) sensors for urban air quality monitoring near transit corridors. The PMS5003 outputs particle counts via UART; the MQ-135 is a cheap analogue gas sensor. In a transport-planning context, these help quantify environmental impact of BRT routes.
  • Study: HC-SR04 ultrasonic for occupancy/distance
    Cheap proximity sensor used to count passengers boarding/alighting a bus or detect vehicle presence in a parking bay. Trigger + Echo pins, measures time-of-flight. Range: 2 cm – 4 m. Quick to wire in Wokwi.

🛰 Communication Protocols

In IoT, the choice of protocol is a first-class architectural decision. HTTP REST is too heavy for constrained devices on unreliable networks.

MQTT — The IoT Standard
  • Deep-study MQTT architecture (QoS 0, 1, 2)
    QoS 0: Fire-and-forget (fast, may lose data). QoS 1: At-least-once (guaranteed delivery, possible duplicates). QoS 2: Exactly-once (4-step handshake, slowest). For high-frequency sensor data (e.g., 10 Hz accelerometer), use QoS 0. For critical alerts (e.g., bridge vibration alarm), use QoS 1. Be ready to justify these choices.
  • Design a topic hierarchy for a fleet system
    Practice designing: fleet/{fleet_id}/vehicle/{vehicle_id}/gps, fleet/{fleet_id}/vehicle/{vehicle_id}/imu, infra/bridge/{bridge_id}/vibration. Wildcards: fleet/+/vehicle/+/gps subscribes to all GPS across the fleet. infra/# gets all infrastructure data.
  • Understand retained messages & last-will testament
    Retained messages: Broker stores the last message on a topic so new subscribers immediately get the latest state (e.g., last known GPS position). Last Will and Testament (LWT): If a sensor disconnects unexpectedly, the broker publishes a pre-configured “offline” message — critical for monitoring fleet health.
  • Hands-on: Send & receive MQTT from Python (paho-mqtt)
    Write a Python script using paho-mqtt that subscribes to uct/sensors/#, logs incoming payloads to a local JSON file, and prints a live dashboard in the terminal. This simulates the cloud-side ingestion you’d build. Time yourself: aim for 15 minutes.
CoAP & Other Protocols
  • Study CoAP vs MQTT trade-offs
    CoAP: UDP-based, RESTful (GET/PUT/POST/DELETE), better for request-response patterns. MQTT: TCP-based, pub/sub, better for continuous streaming. CoAP uses less memory but lacks native pub/sub. For transport telemetry (continuous streams), MQTT wins. For occasional configuration updates to a sensor, CoAP is lighter.
  • Study LoRaWAN for long-range, low-power scenarios
    LoRaWAN: range up to 15 km in rural areas, but only 0.3–50 kbps. Ideal for sensors on remote highway bridges or rural transit stops where there is no Wi-Fi or cellular. Mention this as an option for South African infrastructure monitoring — it shows domain awareness.

💬 Key Talking Points for the Assessment

Strategy

Store-and-forward on the MCU: The ESP32 has built-in flash (4 MB typical) and supports SPIFFS/LittleFS file systems. When MQTT connection is lost, buffer sensor readings to flash. On reconnection, replay the buffer in timestamp order. MQTT QoS 1 ensures the broker acknowledges each message.

RPi gateway buffering: If there’s a Raspberry Pi gateway aggregating multiple ESP32 nodes, it runs a local Mosquitto broker + SQLite buffer. Upstream reconnection triggers a bulk-forward. This is battle-tested in African deployment contexts where cellular can drop for hours.

Your evidence: “At ComputeMore, our Ecoride platform handles ride-tracking over South African mobile networks. We engineered retry logic with exponential backoff and local state persistence — the same principles apply at the hardware layer.”

Technical

Header overhead: An HTTP request carries ~700+ bytes of headers for a 50-byte payload. MQTT’s fixed header is only 2 bytes. At 10 Hz from 100 sensors, that’s 7 MB/min wasted on HTTP headers vs. 20 KB/min with MQTT.

Connection model: HTTP is request-response (client initiates). MQTT maintains a persistent TCP connection with the broker and uses pub/sub — the server can push to the client, and multiple consumers can subscribe to a single data stream without the producer knowing.

QoS guarantees: HTTP has no built-in delivery guarantee beyond TCP ACK. MQTT provides application-level QoS 0/1/2. For critical infrastructure alerts, QoS 1 (at-least-once) is essential.

Bandwidth: On unreliable cellular (EDGE/2G still common in SA rural areas), MQTT’s keep-alive pings are tiny (2 bytes every 30–60s), whereas HTTP would need to re-establish TLS handshakes (~3.5 KB+) for each request.

Architecture

Sensor nodes (3–8 per bridge): ESP32 + MPU-6050 IMU + solar panel + LiPo battery. Each node samples vibration at 100 Hz, computes FFT on-device (edge processing), and only transmits frequency-domain summary (peak frequencies + amplitudes) every 60 seconds via MQTT QoS 1.

Gateway: A weatherproof Raspberry Pi with 4G modem and local Mosquitto broker. Runs a TFLite anomaly-detection model trained on baseline vibration signatures. If anomaly score > threshold, it escalates an immediate alert.

Cloud: Data flows to TimescaleDB (time-series optimised PostgreSQL). A Grafana dashboard shows real-time vibration spectra, historical trends, and red/amber/green health status per bridge.

Cost: Each sensor node ~R800 ($45); RPi gateway ~R2,500 ($140); 4G data plan ~R200/month. Total for a 6-sensor bridge: ~R8,000 hardware + R200/month recurring. Orders of magnitude cheaper than traditional wired structural health monitoring systems.

Your evidence: “SESKA gave me first-principles understanding of structural dynamics — natural frequencies, mode shapes, damping ratios. I know what the sensor data means, not just how to pipe it. And my Ecoride real-time pipeline proves I can build the full ingestion-to-dashboard stack.”
