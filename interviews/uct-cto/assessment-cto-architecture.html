🛠 End-to-End Pipeline Design

Be prepared to design and draw a complete system on a whiteboard. Practice until you can produce a clean diagram in under 10 minutes.

Reference Architecture: Smart Transit Fleet
  • The 6-layer stack (memorise this):
    1. Edge Layer: ESP32 + sensors (GPS, IMU, environmental) → MQTT publish
    2. Gateway Layer: RPi running Mosquitto (local broker) + TFLite anomaly filter
    3. Transport Layer: MQTT → Kafka (bridge adapter). Kafka provides persistence, replay, and fan-out
    4. Processing Layer: Kafka consumers (Python/Faust) implementing windowed aggregations
    5. Storage Layer: TimescaleDB (time-series) + PostGIS (spatial). Continuous aggregates for dashboards
    6. Presentation Layer: Grafana dashboards, alerts via PagerDuty/Slack, API for researchers
  • Open excalidraw.com or app.diagrams.net. Draw the 6-layer pipeline with consistent icons. Label each component. Add arrows showing data flow direction. Export as PNG. Time yourself: aim for 10 minutes. Repeat until it looks professional.
  • Stand at your desk, point at your diagram, and walk through it as if presenting to a panel. Start with: “The system has six layers, each with clear separation of concerns...” Touch each layer: purpose, technology choice, and why that choice over alternatives. End with: “This architecture scales horizontally at every layer.” Record yourself and review.

📊 C4 Model for Communication

The C4 model (Context, Containers, Components, Code) is the industry standard for communicating architecture. Use it to structure all your whiteboard explanations.

C4 Levels
  • Show the system as a single box. Draw external actors: Researchers (query data), Fleet Operators (monitor dashboards), Sensor Network (pushes data), External APIs (weather, traffic). Arrows show who sends what to whom. This is the “10,000-foot view” you start every architecture discussion with.
  • Zoom into the system box. Show the major runtime containers: MQTT Broker, Kafka Cluster, Python Ingestion Service, TimescaleDB + PostGIS, Grafana, Web App (Next.js), Flask ML API. Label the technology on each container. Show communication protocols between them (MQTT, Kafka protocol, SQL, HTTP REST).
  • Zoom into the Python Ingestion Service. Show components: Kafka Consumer, JSON Validator, Anomaly Filter, Batch Writer (COPY to TimescaleDB), Alert Publisher (sends anomaly alerts to Slack). This demonstrates that you think about internal structure, not just black boxes.
  • Level 4 = class/function-level diagrams. Generally only useful when discussing specific algorithms (e.g., the anomaly detection logic or the Haversine function). In the assessment, you’ll mostly stay at Level 2–3. Mention you can go to Level 4 but only when it adds clarity. This demonstrates judgment.

⚖ Scalability & Trade-off Analysis

A CTO never proposes a “perfect” solution. Always articulate trade-offs. Practise verbalising these.

Trade-off Frameworks
  • Consistency, Availability, Partition tolerance — pick two. IoT systems must tolerate network partitions (sensors go offline). So the choice is between consistency and availability. For telemetry dashboards, choose AP (eventually consistent — ok if a reading is 5 seconds late). For safety-critical alerts (bridge failure), choose CP (must be consistent even if availability drops). Be able to articulate both choices.
  • Cloud-only: 100 sensors × 10 Hz × 200 bytes = 200 KB/s = 17 GB/day. At R1.50/GB cellular data = R25/day/sensor = R75,000/month for the fleet. With edge processing: Filter out 95% of redundant/duplicate readings on the MCU. Transmit 850 MB/day. Cost: R3,750/month. Saving: R71,250/month. These are the numbers that make a CTO credible. Practise this calculation until you can do it on a whiteboard in 2 minutes.
  • HTTP REST: Simple, widely understood, but high overhead per request. Good for infrequent config updates. WebSockets: Full-duplex, low latency, but harder on constrained devices (RAM/power). Good for browser→server real-time. MQTT: Purpose-built for IoT. Tiny footprint, QoS guarantees, works on unreliable networks. Best for MCU→broker telemetry. “At ComputeMore, we use SignalR WebSockets for browser real-time, but for hardware sensors on cellular, I’d use MQTT every time.”
  • SQL (TimescaleDB/PostGIS): Rich queries, joins, CTEs, spatial queries. Stronger for multi-dimensional analysis (time + space + vehicle). Learning curve lower for existing SQL teams. NoSQL (InfluxDB): Higher raw write throughput, simpler operations. But no spatial queries, limited joins. Your recommendation: “For a civil-engineering research context where spatial analysis is paramount, TimescaleDB + PostGIS is the right choice. We get full SQL power with PostGIS spatial functions plus time-series optimisation.”

💬 Key Talking Points for the Assessment

Architecture

Three pillars:

  1. Infrastructure & Operations: Maintain departmental servers (compute cluster for simulations, web servers for departmental apps), network, and security. Provide HPC access for researchers. Standard ITIL-aligned ops with runbooks. My SEAT ops + SESKA HPC experience covers this.
  2. Data Science & Engineering: Build and maintain shared data pipelines for research groups. Provide cleaned, queryable datasets (sensor data, traffic counts, survey data) via a departmental data warehouse (PostgreSQL + PostGIS). Offer Python/R training and support for postgrads. My IBM DE cert + SEAT MPI pipeline + PostGIS work covers this.
  3. Software Development: Build custom tools for researchers: dashboards, data-entry web apps, simulation pre/post-processors, experiment management tools. Agile methodology with fortnightly sprints. My ComputeMore full-stack experience + SESKA tooling covers this.

Governance: Monthly steering committee with department leadership. Quarterly roadmap reviews aligned with research priorities. Annual technology radar assessment for emerging tools.

Strategy

Framework I use:

  • Build when: core differentiator for research (unique data pipeline), too niche for off-the-shelf products, or security/compliance requires full control.
  • Buy/Adopt when: commodity functionality (monitoring, CI/CD, email), well-supported open-source exists (Grafana, Mosquitto, PostgreSQL), or team lacks capacity to maintain long-term.
  • Compose (preferred): Combine open-source building blocks (MQTT broker + Kafka + TimescaleDB + Grafana) with custom glue code. This gives flexibility without building from scratch.

Example: “For Ecoride, I composed: off-the-shelf (PostgreSQL, Redis, RabbitMQ, Cloudflare R2) + custom (API services in ASP.NET Core, real-time layer in SignalR, Flutter mobile). This let us ship in months, not years.”

Technical

The reality: University IT has high tech debt — legacy systems, ad-hoc scripts, undocumented configurations. You cannot rewrite everything.

My approach:

  1. Catalogue and classify: Map all existing systems. Classify each as: maintainable (keep), replace (scheduled), or sunset (retire). This is the first thing I’d do in the role.
  2. Strangler fig pattern: Don’t rewrite; wrap. Put a new API layer in front of legacy systems. New consumers use the API. Gradually replace the internals behind the API without disrupting users.
  3. 20% rule: Allocate 20% of each sprint to tech debt reduction. Document one undocumented system per week. Add monitoring to one unmonitored service per week. Steady, compounding improvement.
  4. Security first: Any system with known security vulnerabilities gets prioritised immediately regardless of the roadmap. Non-negotiable.

Evidence: “At SEAT, I inherited a legacy Django system with minimal documentation. I didn’t rewrite it. I added comprehensive logging, migrated to a tested deployment pipeline, documented every integration, and built the MPI data pipeline as an adjacent service that improved the system without touching its core.”
