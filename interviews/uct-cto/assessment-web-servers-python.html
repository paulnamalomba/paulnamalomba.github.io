from django.contrib.gis.db import models as gis_models
from django.db import models

class Vehicle(models.Model):
    vehicle_id = models.CharField(max_length=20, unique=True)
    vehicle_type = models.CharField(max_length=50)
    is_active = models.BooleanField(default=True)

    class Meta:
        ordering = ['vehicle_id']

class GPSPing(models.Model):
    vehicle = models.ForeignKey(Vehicle, on_delete=models.CASCADE, related_name='pings')
    location = gis_models.PointField(srid=4326)
    speed = models.FloatField()
    heading = models.FloatField(null=True)
    timestamp = models.DateTimeField(db_index=True)

    class Meta:
        ordering = ['-timestamp']
        indexes = [
            models.Index(fields=['vehicle', 'timestamp']),
        ]

# sensors/views.py
from rest_framework import viewsets
from rest_framework.decorators import action
from rest_framework.response import Response
from django.db.models import Count, Avg

class VehicleViewSet(viewsets.ModelViewSet):
    queryset = Vehicle.objects.annotate(ping_count=Count('pings'))
    serializer_class = VehicleSerializer

    @action(detail=True, methods=['get'])
    def stats(self, request, pk=None):
        vehicle = self.get_object()
        stats = vehicle.pings.aggregate(
            avg_speed=Avg('speed'),
            total_pings=Count('id')
        )
        return Response(stats)

# config/urls.py
from rest_framework.routers import DefaultRouter
router = DefaultRouter()
router.register(r'vehicles', VehicleViewSet)
urlpatterns += router.urls

Gunicorn — Production WSGI Server
  • Know: Running Django under Gunicorn
    # Basic start (4 workers)
gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 4

# Production configuration
gunicorn config.wsgi:application \
  --bind unix:/run/gunicorn.sock \
  --workers 4 \
  --threads 2 \
  --timeout 120 \
  --access-logfile /var/log/gunicorn/access.log \
  --error-logfile /var/log/gunicorn/error.log \
  --capture-output

# Worker calculation: (2 × CPU cores) + 1
# e.g., 4-core server → 9 workers

uvicorn config.asgi:application --host 0.0.0.0 --port 8000 --workers 4

📸 Flask — Lightweight Alternative

Flask is useful for microservices, data APIs, and quick prototyping. Know when to choose it over Django.

Flask Fundamentals
  • Drill: Minimal Flask API from scratch (5 min)
    # app.py
from flask import Flask, jsonify, request
import psycopg2

app = Flask(__name__)

def get_db():
    return psycopg2.connect(dbname='transport_db', user='paul')

@app.route('/api/health')
def health():
    return jsonify(status='ok')

@app.route('/api/vehicles')
def vehicles():
    conn = get_db()
    cur = conn.cursor()
    cur.execute("SELECT vehicle_id, AVG(speed) as avg_speed FROM gps_pings GROUP BY vehicle_id ORDER BY avg_speed DESC LIMIT 10")
    rows = cur.fetchall()
    conn.close()
    return jsonify([{'vehicle': r[0], 'avg_speed': round(r[1], 1)} for r in rows])

@app.route('/api/pings', methods=['POST'])
def create_ping():
    data = request.get_json()
    conn = get_db()
    cur = conn.cursor()
    cur.execute(
        "INSERT INTO gps_pings (vehicle, lat, lon, speed) VALUES (%s, %s, %s, %s)",
        (data['vehicle'], data['lat'], data['lon'], data['speed'])
    )
    conn.commit()
    conn.close()
    return jsonify(status='created'), 201

if __name__ == '__main__':
    app.run(debug=True, host='0.0.0.0', port=5000)

# app/__init__.py
from flask import Flask
from flask_sqlalchemy import SQLAlchemy

db = SQLAlchemy()

def create_app(config='app.config.ProductionConfig'):
    app = Flask(__name__)
    app.config.from_object(config)
    db.init_app(app)

    from .routes.vehicles import vehicles_bp
    from .routes.pings import pings_bp
    app.register_blueprint(vehicles_bp, url_prefix='/api')
    app.register_blueprint(pings_bp, url_prefix='/api')

    return app

# wsgi.py

app = create_app()

# Run with: gunicorn wsgi:app --bind 0.0.0.0:5000 --workers 4

⚙️ WSGI vs ASGI — Understanding the Stack

Application Server Concepts
  • Understand the request flow: Browser → Nginx → Gunicorn → Django
    Browser/curl → Nginx (port 80/443)
                  ↓ (proxy_pass)
               Gunicorn (unix socket or port 8000)
                  ↓ (WSGI callable)
               Django (config.wsgi:application)
                  ↓
               View → ORM → PostgreSQL → Response

WSGI: Synchronous. One request per thread/worker. Gunicorn, uWSGI.
ASGI: Asynchronous. WebSockets, long-polling, async views. Uvicorn, Daphne, Hypercorn.
    Rule of thumb: Use WSGI (Gunicorn) unless you need WebSockets or async views. SEAT uses WSGI because all operations are standard request/response.
  • Know: Static files and media in production
    # Django: collect static files
python manage.py collectstatic --noinput
# Creates ./staticfiles/ directory

# Nginx serves static files directly (no Django involvement)
# In nginx config:
location /static/ {
    alias /opt/transport_api/staticfiles/;
    expires 30d;
    add_header Cache-Control "public, immutable";
}

location /media/ {
    alias /opt/transport_api/media/;
}

# Everything else goes to Gunicorn
location / {
    proxy_pass http://unix:/run/gunicorn.sock;
}

💬 Key Talking Points

Technical

Django when you need: ORM for complex data models, built-in admin panel for operations teams, authentication/authorization out of the box, GIS support (PostGIS), established patterns for larger teams. SEAT is Django because it’s a full platform with 15+ models, role-based auth, and an admin dashboard.

Flask when you need: a lightweight data API with 2–3 endpoints, a microservice in a larger architecture, maximum flexibility on dependencies, rapid prototyping where Django’s boilerplate is overkill.

Your evidence: “SEAT is Django because we needed the full framework — ORM, admin, auth, GIS. When I build internal data pipeline APIs or health check endpoints, I use Flask because I need a single file that returns JSON from a PostgreSQL query.”

Technical

Django’s runserver is single-threaded, has no connection pooling, no worker management, and is explicitly marked “not for production” in the Django docs. Gunicorn pre-forks multiple worker processes, each handling requests independently. If one worker crashes (e.g., OOM on a large query), the master process respawns it. Combined with Nginx as a reverse proxy for TLS termination, static file serving, and connection buffering, this is the standard production deployment pattern.
