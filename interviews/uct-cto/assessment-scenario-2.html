🚀 Task 1: Optimizing a Slow SQL Query

Gold Standard Solution:

The system is suffering from the classic "N+1 Database Query Problem." Because Django querysets are lazy and retrieve related objects on-demand, executing a loop over 3,000 students to print their Advisor's name will trigger 1 query to get the students, and 3,000 additional queries to fetch each individual Advisor's details.

# INELLIGENT/NAIVE APPROACH (Triggers N+1)
# 1 query for students + 3000 queries for advisors
students = Student.objects.filter(department='CIV')
for student in students:
    print(student.advisor.name) 

# GOLD STANDARD OPTIMIZATION (2 DB hits total)
# 1. select_related() forces a SQL SQL INNER/LEFT JOIN to fetch ForeignKeys instantly.
# 2. prefetch_related() executes a separate query for reverse/Many-To-Many relations 
#    and does the "join" efficiently in Python memory.
students = Student.objects.filter(department='CIV').select_related('advisor').prefetch_related('course_registrations')

for student in students:
    print(student.advisor.name) # No DB hit required!
    for course in student.course_registrations.all():
        print(course.code) # No DB hit required!

Bonus Deep-Technical Points to Mention:

  • Pagination: 3,000 records should never be shipped to the frontend simultaneously. Implement django.core.paginator.Paginator to fetch records in chunks of 50.
  • .values() or .values_list(): If the frontend only needs raw data (e.g., student ID and name) for an API response, using .values('student_number', 'first_name') skips the massive overhead of instantiating thousands of complex Django Model Objects in Python memory, returning lightweight dictionaries instead.

🔄 Task 2: Python Utility Script for Legacy Integration

Gold Standard Solution (Batch Processing vs. Event-Driven Architecture):

1. Traditional Batch Architecture: I would write a Custom Django Management Command (e.g., python manage.py sync_peoplesoft) and execute it via a Linux cron job. Because the file is large, I will not load the whole CSV into Python memory at once.

import csv
from django.core.management.base import BaseCommand
from django.db import transaction
from myapp.models import Student

class Command(BaseCommand):
    help = 'Syncs nightly CSV from legacy FTP'

    def handle(self, *args, **kwargs):
        # In actual prod, retrieve file via ftplib here
        file_path = '/tmp/nightly_dump.csv'
        
        batch_size = 2000
        batch = []
        
        # 1. Use memory-efficient generators/iterators to read massive files line-by-line
        with open(file_path, 'r') as file:
            reader = csv.DictReader(file)
            
            for row in reader:
                # 2. Clean inputs using Python dictionary parsing 
                student = Student(
                    student_number=row['std_id'].strip(),
                    email=row['email'].lower().strip(),
                    is_active=row['status'] == 'ENROLLED'
                )
                batch.append(student)
                
                # 3. Insert in safe chunks to prevent DB RAM overflow
                if len(batch) >= batch_size:
                    # 4. Wrap inserts in atomic Transactions to prevent partial ghost data
                    with transaction.atomic():
                        # Use bulk_create() instead of saving row-by-row (massively faster)
                        Student.objects.bulk_create(batch, ignore_conflicts=True)
                    batch = [] # Reset memory chunk
            
            # Catch remaining records outside the loop multiplier
            if batch:
                with transaction.atomic():
                    Student.objects.bulk_create(batch, ignore_conflicts=True)
                    
        self.stdout.write(self.style.SUCCESS("Nightly Sync Complete!"))

2. Event-Driven Architecture (Applying Message Queuing):

A more robust, distributed approach utilizes Apache Kafka or Apache ActiveMQ. Rather than a monolithic cron script handling file parsing and DB inserting synchronously, we decouple the tasks:

  • Producer: A lightweight service detects the FTP drop, reads the CSV via stream, and publishes each row as a JSON event to an ActiveMQ/Kafka topic (e.g., student.records.incoming).
  • Consumer (Celery Worker Daemons): Dedicated Celery worker processes (running independently from the Gunicorn application server) subscribe to this topic. As messages arrive, Celery workers—configured with specific worker_prefetch_multiplier limits to govern memory flow—deserialize the JSON and aggressively use bulk_create to insert into PostgreSQL. This guarantees the Gunicorn web threads are never blocked by heavy data ingestion.

Benefit: This message queuing architecture enables decoupled scaling. If the DB is locked or slow, Kafka perfectly buffers the data flow safely on disk, eliminating the risk of a timeout crashing a 50MB bulk script halfway through.

(Equivalent JS approach: Utilize fs.createReadStream to pipe the CSV data, parse it row-by-row, and use Prisma's createMany or distribute JSON payloads to a Kafka producer using kafkajs.)

🛡️ Task 3: Application Security & Compliance

Gold Standard Solution:

1. Environmental Separation & Secrets Management

  • No Hardcoded Secrets: Django's SECRET_KEY, DB credentials, and external API keys must be loaded purely via environment variables (e.g., python-dotenv) or a secrets manager like HashiCorp Vault. Under no circumstances should they be committed to GitHub.
  • Production Toggles: Ensure DEBUG = False in production. Having DEBUG on leaks detailed server stack traces to users on error, essentially providing attackers a map of the backend architecture.

2. Network Level Security

  • Database Isolation: PostgreSQL should never be exposed to the public internet. It should bind only to localhost (127.0.0.1) or be isolated within a private Virtual Private Cloud (VPC), allowing only inbound connections from the specific IP address of the App Server.
  • Reverse Proxy Constraints: Configure a Reverse Proxy (such as Apache2/Nginx) to intercept all incoming traffic. This proxy sits at the edge of the network, protecting the App Server's IP address, providing load balancing, and handling CPU-intensive SSL/TLS decryption (SSL Termination). It must serve Django exclusively over HTTPS (TLS 1.2+). Set Django's SECURE_SSL_REDIRECT = True, SESSION_COOKIE_SECURE = True, and enforce HSTS (HTTP Strict Transport Security).

3. Application Level Security (The OWASP Top 10)

  • SQL Injection: Django's ORM inherently prevents SQL injection by parameterizing underlying database queries via psycopg2. However, I would strictly forbid the use of Django's .raw() SQL method in the codebase without rigorous peer review.
  • XSS (Cross-Site Scripting): Django templates auto-escape variables. I would audit the codebase to ensure developers are not recklessly bypassing this protection using the |safe filter on user-provided inputs.
  • CSRF (Cross-Site Request Forgery): Ensure CsrfViewMiddleware is active and that all forms mutating data (POST, PUT, DELETE) include the {% csrf_token %} template tag.

4. Authentication & Auditing (POPIA Defense)

  • LDAP Binding: Authentication should rely entirely on UCT's Active Directory. Using local database passwords for staff is a liability if a staff member gets terminated. LDAP handles instantaneous lockouts.
  • Audit Logging: For highly sensitive data (like altering a student's grade status), implement a library like django-simple-history. This tracks exactly who changed a record and when, establishing an immutable paper trail crucial for POPIA compliance forensic audits.
