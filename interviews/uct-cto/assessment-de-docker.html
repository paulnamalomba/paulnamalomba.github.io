🌎 Spatial Data & PostGIS

Transport planning is inherently spatial. Every vehicle GPS ping, every bus stop, every road segment is a geo-object. PostGIS turns PostgreSQL into a spatial database engine.

PostGIS Fundamentals
  • Set up PostgreSQL + PostGIS locally (Docker)
    Run: docker run -d --name postgis -p 5432:5432 -e POSTGRES_PASSWORD=iot postgis/postgis:16-3.4. Connect with pgAdmin or psql. Verify: SELECT PostGIS_Version();. This gives you a full spatial database in 30 seconds.
  • Practice: Create spatial tables with POINT & LINESTRING
    Create a vehicle_pings table with a GEOMETRY(Point, 4326) column. Insert 1,000 synthetic GPS pings along a route (use ST_MakePoint(lon, lat)). Create a routes table with GEOMETRY(LineString, 4326). SRID 4326 = WGS84 (standard GPS coordinate system).
  • Practice 5 essential PostGIS queries
    1. ST_Distance(a.geom, b.geom) — distance between two points.
    2. ST_DWithin(geom, ST_MakePoint(18.42, -33.93)::geography, 500) — find all pings within 500m of a bus stop.
    3. ST_Buffer(geom, 0.005) — create a geofence around a route.
    4. ST_Intersection / ST_Contains — which vehicles are inside a zone.
    5. ST_MakeLine(geom ORDER BY ts) — reconstruct a vehicle trajectory from GPS pings.
  • Understand GiST spatial indexing
    CREATE INDEX idx_pings_geom ON vehicle_pings USING GIST(geom); — GiST (Generalized Search Tree) indexes bounding boxes of geometries for O(log n) spatial lookups. Without it, every ST_DWithin query does a full table scan. Know this trade-off — it parallels your B-tree indexing knowledge from SEAT PostgreSQL work.
  • Complete the official PostGIS workshop (Chapters 1–8)
    Go to postgis.net/workshops/postgis-intro. Work through Chapters 1–8 (geometries, spatial relationships, spatial joins, indexing). Budget 90 minutes. This is the single highest-ROI preparation activity for the assessment.

🚀 Data Ingestion & Message Brokers

High-throughput sensor streams cannot be written directly to a database — you need a buffer layer.

Apache Kafka
  • Study Kafka core concepts (topics, partitions, consumer groups)
    Topics: Named streams (e.g., gps-pings, vibration-data). Partitions: Topics are split into partitions for parallelism. GPS data can be partitioned by vehicle_id to guarantee ordering per vehicle. Consumer groups: Multiple consumers share the load — one group writes to TimescaleDB, another feeds a real-time dashboard. Messages are retained (default 7 days) even after consumption.
  • Know Kafka vs RabbitMQ trade-offs (you use RabbitMQ)
    RabbitMQ: Smart broker, dumb consumer. Messages are deleted after ACK. Best for task queues and command routing. Kafka: Dumb broker, smart consumer. Messages are an immutable log. Best for high-throughput event streaming and replay. For IoT telemetry (millions of events/sec, need to replay history), Kafka wins. For Ecoride ride-request dispatching, RabbitMQ was the right choice. Be able to articulate this.
  • Hands-on: Run Kafka locally with Docker Compose
    Use the Confluent docker-compose.yml (Zookeeper + Kafka + Schema Registry). Create a topic sensor-data, produce 1,000 JSON messages with a Python producer (confluent-kafka library), consume them with a Python consumer, and write to a CSV. Time yourself: aim for 30 minutes setup-to-working.
Stream Processing
  • Study stream processing patterns (windowing, aggregation)
    Tumbling windows: Fixed-size, non-overlapping (e.g., average speed every 60 seconds). Sliding windows: Overlapping (e.g., rolling 5-minute average). Session windows: Activity-based (e.g., group GPS pings into “trips” by detecting >5 min stationary gaps). These are the primitives you’ll need for time-series aggregation at the assessment.
  • Practice: Python stream processing with Faust or plain Kafka consumer
    Write a Kafka consumer that implements a 60-second tumbling window: collect all GPS pings in the window, compute average speed and total distance (Haversine formula), and write the aggregated result to a trip-summaries topic. This demonstrates your ability to process data in-flight.

📈 Time-Series Storage

Standard PostgreSQL chokes on millions of rapid time-stamped inserts due to B-tree index bloat. Time-series databases solve this with automatic partitioning.

TimescaleDB
  • Study TimescaleDB hypertables & chunks
    TimescaleDB is a PostgreSQL extension. SELECT create_hypertable('sensor_data', 'time'); transparently partitions data into time-based chunks (default 7 days). Queries automatically prune irrelevant chunks. INSERT rates 10–100× faster than vanilla PostgreSQL on time-series workloads. You retain full SQL compatibility.
  • Hands-on: Set up TimescaleDB & create a hypertable
    docker run -d --name timescale -p 5433:5432 -e POSTGRES_PASSWORD=iot timescale/timescaledb:latest-pg16. Create a gps_pings hypertable with columns: time TIMESTAMPTZ, vehicle_id TEXT, lat DOUBLE PRECISION, lon DOUBLE PRECISION, speed FLOAT. Insert 100K synthetic rows using a Python script.
  • Practice: Continuous aggregates for dashboard queries
    Create a continuous aggregate: CREATE MATERIALIZED VIEW hourly_speed WITH (timescaledb.continuous) AS SELECT time_bucket('1 hour', time) AS bucket, vehicle_id, avg(speed), max(speed) FROM gps_pings GROUP BY bucket, vehicle_id;. This pre-computes dashboard queries — O(1) instead of scanning millions of rows. Explain this as a CTO-level optimization in the assessment.
  • Study: Data retention policies & compression
    SELECT add_retention_policy('gps_pings', INTERVAL '90 days'); automatically drops old chunks. ALTER TABLE gps_pings SET (timescaledb.compress); enables columnar compression (typically 10–20× storage reduction). Hot data stays uncompressed for fast writes; cold data compresses for cheap storage. Know these numbers for the assessment.
InfluxDB (Alternative – Know the Trade-off)
  • Study: InfluxDB vs TimescaleDB comparison
    InfluxDB: Purpose-built NoSQL TSDB. Own query language (Flux/InfluxQL). Excellent write performance, built-in downsampling. TimescaleDB: PostgreSQL extension. Full SQL. Joins, CTEs, window functions all work. PostGIS integration for spatial+temporal queries. For your use case (GPS + time-series + spatial), TimescaleDB + PostGIS is unbeatable because you get spatial and temporal queries in one database.

🐍 Python Data Processing

Dr. Nnene will likely give you messy, real-world CSVs. Be fluent in Pandas for rapid data wrangling.

Pandas & NumPy Fundamentals
  • Practice: Load, inspect, and clean a messy CSV (15 min drill)
    Download a traffic/sensor dataset from Kaggle (search “urban traffic” or “sensor telemetry”). Practice: df.info(), df.describe(), df.isnull().sum(), handle NaNs with df.fillna(method='ffill') (forward-fill — appropriate for time-series), remove duplicates, parse timestamps. Time yourself. Aim for fluency, not perfection.
  • Practice: GroupBy aggregations and resampling
    df.set_index('timestamp').resample('1H').agg({'speed': 'mean', 'distance': 'sum'}) — resample time-series to hourly buckets. df.groupby('vehicle_id')['speed'].agg(['mean', 'max', 'std']) — per-vehicle statistics. These are the queries you’ll need to produce quickly under assessment conditions.
  • Practice: Simple anomaly detection (Z-score & IQR)
    Compute Z-scores: df['z_speed'] = (df['speed'] - df['speed'].mean()) / df['speed'].std(). Flag rows where |z| > 3. Or use IQR: Q1 = df['speed'].quantile(0.25), Q3 = df['speed'].quantile(0.75), IQR = Q3 - Q1, flag speed < Q1 - 1.5*IQR or speed > Q3 + 1.5*IQR. Both approaches handle noisy sensor data — mention you’d apply this at the edge (MCU) for lighter anomalies and in the pipeline for statistical ones.
  • Code: Haversine distance function from memory
    Write the Haversine formula for great-circle distance between two lat/lon points. This will almost certainly appear in a geospatial assessment. Memorise:
    a = sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2)
    d = 2R · atan2(√a, √(1-a)) where R = 6,371 km. Practice implementing this as a vectorised NumPy function.
  • Practice: GeoPandas for spatial DataFrame operations
    import geopandas as gpd. Convert a Pandas DataFrame to a GeoDataFrame: gdf = gpd.GeoDataFrame(df, geometry=gpd.points_from_xy(df.lon, df.lat), crs='EPSG:4326'). Plot trajectories on a map with gdf.plot(). Perform spatial joins: find all GPS pings within 200m of bus stops. This bridges your PostGIS knowledge with Python fluency.

⚡ Your Killer Evidence: MPI Data Pipeline

This is your single most powerful data-engineering story. Polish it until it’s razor-sharp.

Narrative Preparation
  • Rehearse: The Problem (30 seconds)
    “SEAT’s registration system needed to ingest ~30 million rows of student/course data from CSV exports into PostgreSQL. The single-threaded Python loader took 3 hours, which was unacceptable during registration windows where the system needed to be live.”
  • Rehearse: The Solution (60 seconds)
    “I engineered a parallel pipeline using MPI (mpi4py) with hyperthreading. The CSV was chunk-partitioned across N worker processes. Each worker processed its chunk with batch-optimised INSERTs (COPY protocol where possible, otherwise multi-row VALUES batches of 5,000 rows). Memory was managed via chunked reads (pandas chunksize=50,000) to prevent OOM on the server. Workers committed independently, and a coordinator process tracked progress.”
  • Rehearse: The Result (30 seconds)
    “Load time went from 3 hours to 25 minutes — a 7.2× speedup. More importantly, this meant we could run the data pipeline multiple times during a registration cycle for updates, rather than being limited to a single overnight batch. It changed the operational model.”
  • Rehearse: The Bridge to IoT (20 seconds)
    “The same principles — partition data, parallelise ingestion, batch writes, manage memory — apply to IoT sensor pipelines. Instead of CSV chunks, the partitions are Kafka topic partitions. Instead of MPI workers, they’re Kafka consumer group members. The pattern is identical, just the transport layer changes.”

💬 Key Talking Points for the Assessment

Architecture

You don’t write directly to the database. That’s 10,000 INSERT/s — your PostgreSQL connection pool will be exhausted in seconds.

Layer 1 (Buffer): All sensor data goes to Kafka. Partitioned by sensor_id % 32 (32 partitions). Kafka handles 100K+ messages/sec trivially.

Layer 2 (Consumer group): 8 Python consumer processes (one per 4 partitions). Each consumer batches 5,000 rows in memory, then bulk-inserts using COPY protocol. This turns 10,000 individual INSERTs into 2 COPY operations/sec. Exactly the same batch-chunked pattern I used in the SEAT MPI pipeline.

Layer 3 (TimescaleDB): Hypertable with 1-hour chunks, continuous aggregates for dashboards, 90-day retention. Compressed cold data for long-term trends.

Back-pressure: If consumers lag, Kafka retains data (7-day retention), so nothing is lost. Add more consumers to scale horizontally.

Technical

SELECT v.vehicle_id, v.speed, v.time,
       ST_Distance(v.geom::geography, s.geom::geography) AS dist_m
FROM gps_pings v
JOIN bus_stops s ON ST_DWithin(v.geom::geography, s.geom::geography, 500)
WHERE v.time > NOW() - INTERVAL '5 minutes'
  AND s.stop_name = 'Civic Centre MyCiTi';

Why this is fast: GiST index on v.geom prunes 99%+ of rows spatially. TimescaleDB chunk exclusion prunes all but the latest chunk temporally. The query scans perhaps 500 rows out of millions.

Cast to geography: ::geography ensures ST_DWithin uses metres (geodesic distance), not degrees. Without the cast, 500 means 500 degrees, which is nonsensical. This is a common gotcha — mentioning it proactively shows mastery.
